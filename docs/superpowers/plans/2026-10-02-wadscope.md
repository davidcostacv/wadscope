# WADScope Implementation Plan

> **For agentic workers:** Use the executing-plans skill to implement this plan task by task in the current chat. Steps use checkboxes for tracking. Complete the research gate before implementing behavior that depends on a finding.

**Goal:** Deliver a usable WAD inspector, a reproducible reverse engineering investigation, and a portfolio-ready v0.1.0 release that the author can explain in an interview.

**Architecture:** A Python library owns parsing, validation, extraction, and classic map geometry. A thin CLI exposes those operations; an SVG exporter consumes validated geometry. Research notes connect implemented behavior to binary evidence and explicitly distinguish inspector safety rules from observed engine behavior.

**Tech stack:** Python 3.11+ as the proposed minimum, standard library at runtime, `unittest` for tests, Ghidra for static analysis, Git and GitHub Actions. Confirm Python and Ghidra requirements during environment setup before installing anything.

## Starting point and priorities

The GitHub repository exists and contains README.md, LICENSE, and .gitignore. No implementation, experiments, or test results exist yet.

Success means the author can demonstrate the tool, explain three evidence-backed findings, reproduce the results, and discuss a corrected hypothesis or meaningful limitation. A first release takes priority over adding a GUI, AI features, or a 3D viewer.

Planning assumptions: beginner in reverse engineering, Windows PowerShell, and 6–10 hours per week. Estimate 40–65 hours over roughly 5–9 weeks if basic Python is familiar; allow additional learning time otherwise. Adjust estimates after the first milestone using actual time spent.

## Working agreement and cost control

- Use PowerShell syntax in every user-facing terminal instruction. Avoid Bash activation commands and Unix-only utilities.
- Keep runtime and research tooling local; no paid API is required by the project.
- Use the standard library first. Add a dependency only when it removes a demonstrated maintenance or correctness problem.
- Offer two execution styles: **local/manual**, where scripts and tools consume no LLM tokens, and **AI-assisted**, where short requests help review code or interpret selected evidence. Both require human verification. Local tools may still have compute, download, or hosting costs.
- Prefer deterministic scripts for hashing, fixtures, extraction comparisons, and benchmarks. Do not ask an LLM to perform repetitive byte calculations.
- Send AI only relevant functions, byte ranges, and failure output, rather than whole binaries or repeated repository dumps.
- Measure performance before optimizing. Parse the directory once; read only selected resource bytes for extraction; avoid copying an entire archive unnecessarily.
- Keep `docs/research/lessons.md`: record a mistake, its cause, the fix, and the regression check. Add entries only for observed mistakes.
- For GitHub CLI publication, distinguish the sandbox Git owner from the authenticated Windows user. If necessary, scope `safe.directory` to the individual command and exact repository. Do not change global trust settings.
- Do not use `NUL` as `core.excludesFile`; it failed in this environment. An empty override (`git -c core.excludesFile= status --short`) successfully checks this repository.
- Commit each coherent, verified milestone; publish changes to the existing repository. Never label planned work as finished.

Proposed interfaces, to lock after research: `WadArchive.open(path)` is a context manager exposing ordered entries and `read_lump(index)`. Each entry has its original index, raw name bytes, display name, offset, and size. `extract_lump(archive, index, destination, overwrite=False)` returns the output path. `load_map(archive, marker_index)` returns validated vertices and lines. `render_svg(geometry)` returns SVG text. `cli.main(argv=None)` returns an exit code. Preserve entry order and repeated names; indexes identify extraction targets without ambiguity.
